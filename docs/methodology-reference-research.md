# DSHEval 方法页参考调研

更新日期：2026-09-02
调研范围：HELM、SWE-bench、GAIA、AgentBench、Chatbot Arena / Arena 的官方项目页、官方文档、论文与代码仓库。本文只讨论 DSHEval 方法页的信息结构和可信度表达，不规定视觉稿。

## 结论

成熟 benchmark 的信任不是靠“严谨、真实、透明”等形容词建立的，而是靠用户能迅速找到五类可核对信息：

1. 评测对象和不评测的范围；
2. 对每个对象做了什么；
3. 用什么规则判定成功、失败和无法判定；
4. 对比条件、版本、样本量和异常处理；
5. 从汇总结论通往原始记录、评分依据和局限的路径。

对 DSHEval 而言，最合适的不是继续美化当前“测试前 / 测试中 / 判分时 / 发布时”四行流程，而是将方法页改成一个简短的“公开评测契约”：先说清统一规则，再将记忆、搜索、Deep Research 等不同测试的具体协议下沉到独立页。

## 成熟项目如何组织方法信息

### 1. HELM：先说原则，再展开可检查的运行细节

HELM 的总介绍先用三个原则定义“holistic evaluation”：覆盖面与不完整性、多指标测量、标准化。它不只说覆盖广，还明示哪些场景和指标未覆盖，并强调模型间的适配方式应受控。结果端允许从汇总统计下钻到原始 prompt 和模型输出。
来源：[HELM 官方介绍](https://crfm.stanford.edu/2022/11/17/helm.html)

HELM Instruct 的方法段落则把抽象原则落到四类对象：场景、被测模型、评估者、评估准则；随后公布具体评分题、评分选项、人类评估者筛选和标注量。页尾再提供原始回答和评分浏览入口。
来源：[HELM Instruct 官方方法与结果页](https://crfm.stanford.edu/2024/02/18/helm-instruct.html)

可借鉴：总方法讲稳定原则，具体协议讲任务、评分和运行细节；明说“没测什么”；从结论可追溯至单次运行。

不适合照搬：HELM 的学术分类体系、大量组合矩阵和多层 leaderboard 会让 DSHEval 显得更像论文门户；DSHEval 当前的核心优势是少量真实任务的证据深度，不是场景数量。

### 2. SWE-bench：先用一个可执行闭环说清“怎样算解决”

SWE-bench 项目页用三步说清整个评测闭环：从真实 GitHub issue 与 PR 构造任务；在 PR 基础 commit 上构建 Docker 环境；将 issue 交给系统修改代码，再通过 `FAIL_TO_PASS` 测试判断问题是否解决。这个简化闭环同时说清了输入、环境、动作和成功信号。
来源：[SWE-bench 官方项目页](https://www.swebench.com/original.html)

它把操作型信息放到独立文档：评测指南给出输入格式、执行命令、Docker 环境、结果文件和每个计数字段的定义；并明确区分“未提交预测”、“测试未通过”、“无法产生结果”和“可能的基础设施故障”。
来源：[SWE-bench 官方 Evaluation Guide](https://www.swebench.com/SWE-bench/guides/evaluation/)

SWE-bench Verified 还通过公布质量筛选过程建立信任：筛查问题是否信息不足、测试是否会错杀有效解，说明标注人员、独立复核数和保守合并规则，并发布标注和 rubric。
来源：[Introducing SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/)

可借鉴：用“输入 → 执行 → 判定”的闭环取代抽象口号；把结果失败和评测故障分开；如果声称“已核查”或“已复测”，必须同时给出核查规则。

不适合照搬：Docker、CLI 命令、JSONL 和日志目录不应进入 DSHEval 面向普通用户的主方法页；这些内容应属于复现文档或测试详情。另外，公开固定题库可能受污染影响，即使是 Verified 集合也需要持续审计，不应把“已验证”当作永久质量保证。
来源：[OpenAI 对 SWE-bench Verified 后续局限的官方审计](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)

### 3. GAIA：用任务设计原则解释“分数为什么有意义”

GAIA 的方法叙事并不从流程开始，而是先解释题目设计的四个原则：对人类概念上简单、来自真实使用、可解释、不易通过记忆或穷举取巧；回答被设计为简短且无歧义，因而能用近似精确匹配自动评分。页面后续才讲能力覆盖、三档难度、出题和双重独立校验。
来源：[GAIA 官方论文项目页](https://arxiv.org/abs/2311.12983)

官方数据卡将榜单、问题数据和附件格式放在独立资源中，没有把运行层细节堆在项目叙事前。
来源：[GAIA 官方数据卡](https://huggingface.co/datasets/gaia-benchmark/GAIA/blob/main/README.md)

可借鉴：说明题目如何对应真实需求、为什么可判定、为什么不容易取巧；为任务给出一个短例子，让用户能直观检验规则。

不适合照搬：GAIA 为榜单隐藏大量答案，这有助于降低泄题，但 DSHEval 的现阶段卖点是公开可复查证据，不宜照搬“只公布总分、隐藏依据”。如果未来为了防污染轮换题库，也应公布题库版本、更新日期、抽样原则和已退役题目的证据。

### 4. AgentBench：用任务环境定义能力，而不是用抽象标签

AgentBench 的入口先列出八个具体环境，再给出数据划分、榜单、快速开始和引用。详细文档逐个解释任务环境、交互方式和主要指标；例如操作系统与数据库任务都用完成率作为主指标。框架文档则另说明任务环境、Agent 和调度客户端如何交互。
来源：[AgentBench 官方仓库](https://github.com/THUDM/AgentBench)、[AgentBench 官方详细说明](https://github.com/THUDM/AgentBench/blob/main/docs/Introduction_en.md)

可借鉴：用可感知的环境和任务描述能力，例如“在新会话找回旧信息”，而不是只写“记忆能力”。

不适合照搬：AgentBench 的 README 将研究介绍、榜单、安装、Docker 资源和服务架构放在很长的单页中，信息可查但不利于非研究者快速理解。DSHEval 应保留“具体环境”的表达，但把运行架构与资源需求下沉到复现文档。

### 5. Chatbot Arena / Arena：将用户流程、排名统计和榜单政策拆开

Arena 的面向普通用户页只用四个动作说明交互：输入问题、比较两个匿名回答、投票、显示模型身份并继续。同页把透明度与隐私政策、开放数据和研究论文放在流程之后。
来源：[Arena 官方 How It Works](https://arena.ai/how-it-works)

具体统计方法则由论文承担：它交代匿名随机对战、成对偏好、模型对采样、Bradley–Terry 排名、置信区间以及人群与专家投票一致性分析。
来源：[Chatbot Arena 官方论文](https://arxiv.org/abs/2403.04132)

榜单政策再独立说明入榜条件、票数稳定要求、预发布模型标记、采样政策、退役策略、数据发布与方法变更记录。榜单本身在分数旁显示误差、票数和排名区间，而不只展示一个精确名次。
来源：[Arena Leaderboard Policy](https://arena.ai/blog/policy/)、[Arena Text Leaderboard](https://arena.ai/leaderboard/text)

可借鉴：普通用户流程保持极短；把数据、版本和不确定性放在结果附近；为入榜、更新、退役和方法修订建立可查规则。

不适合照搬：DSHEval 的核心是按预设标准验证任务完成，不是用户偏好；不应照搬匿名对战、投票、Elo/BT 分数或“人更喜欢哪个”的叙事。在 DSHEval 样本量较小时，也不应用复杂统计外观制造虚假精度。

## 适合 DSHEval 的 7 个结构原则

### 原则 1：首屏必须定义“测什么”，不只宣告态度

建议首屏只承担三个信息：

- 对象：真实可用的 Agent 与插件；
- 单元：在固定条件下完成同一组真实任务；
- 输出：可复查的完成结果、失败原因与证据。

标题可以有态度，但副标题必须能独立说清上述三点。HELM、SWE-bench 和 GAIA 都在入口页很快定义测试对象与成功信号。

### 原则 2：只保留一个主流程，每步都写成可观察动作

建议主流程是：

`1. 锁定版本与条件 → 2. 执行预定任务 → 3. 按事先公布的标准判定 → 4. 发布记录、异常与限制`

每步要回答“产生什么可检查的东西”，不宜再增加第二套卡片流程、时间线或装饰性路径。

### 原则 3：把“控制变量”展开成明确对照表

最小可用结构是三类：

| 类型 | DSHEval 需公布的内容 |
| --- | --- |
| 同一次对比中固定 | 题目、运行环境、模型配置、超时、评分规则 |
| 允许变化 | 被测 Agent / 插件、其公开版本与产品自身的必需配置 |
| 不能直接比较 | 不同日期、不同模型、不同题库版本或明确变更过的测试 |

“控制变量”不应只停留在标题。HELM 的标准化原则和 SWE-bench 的容器化环境都是对这个问题的具体回答。

### 原则 4：给评分和异常一组稳定、互斥的状态

至少区分：

- 任务通过：满足事先定义的所有必需条件；
- 任务未通过：评测正常完成，但结果未达标；
- 无法评测：对象本身缺少必需能力或入口；
- 评测故障：网络、账号、工具、环境或脚本问题阻止了有效判定；
- 已补测 / 已修正：说明触发条件、原条件是否保持及对排名的影响。

SWE-bench 对运行结果的分类表明，评测故障不应被记为被测对象的失败。

### 原则 5：“可复查”必须对应一份明确的证据包

总方法页只需要定义每次公开结果至少包含什么，例如：

- 被测对象、版本与测试日期；
- 任务文本与必需输入；
- 运行过程、输出或截图；
- 判定标准、实际结果与通过 / 未通过依据；
- 异常、人工介入、补测和已知限制。

具体文件结构、截图规格和日志字段放到测试详情或复现文档。HELM 从汇总结果下钻到原始输入输出的做法，比在方法页重复展示大量证据更适合 DSHEval。

### 原则 6：总方法与专项协议分层，页面之间不重复

总方法页只讲所有评测共享的规则；记忆、搜索、Deep Research 等专项页再讲：

- 任务如何选取与分类；
- 专项运行模式；
- 题目级判定规则；
- 该类测试特有的失败与限制；
- 典型任务与实际证据入口。

这对应 HELM 的“总原则—具体 leaderboard / protocol”、SWE-bench 的“项目概览—运行文档”与 Arena 的“用户流程—统计论文—榜单政策”分层。

### 原则 7：把局限、版本和更新规则视为方法本身

方法页底部应用简短条目回答：

- 当前未覆盖哪些任务、平台或使用方式；
- 当产品版本、基底模型或网站行为改变时，什么情况下复测；
- 方法修订如何记录，新旧结果能否直接比较；
- 如何反馈错误或申请复核。

HELM 把“认识不完整”放在核心原则中；Arena 将方法变更、预发布状态和模型退役写成政策。对快速变动的 Agent 产品来说，这些信息比“永久公平”式承诺更可信。

## 建议的 DSHEval 方法页顺序

以一条纵向阅读路径组织，不做多列信息墙：

1. **定义**：一句话说清测试对象、真实任务和可复查输出。
2. **什么固定，什么会变**：一张三行对照表。
3. **一次评测怎样完成**：一条四步主流程，每步一句。
4. **怎样判分**：定义通过、未通过、无法评测、评测故障；用一个实例演示规则。
5. **我们公布什么**：一份五项证据包清单，链接到完整结果。
6. **专项评测协议**：将记忆、搜索、Deep Research 等作为简洁索引，不在此复述细节。
7. **局限与更新**：当前边界、方法版本、更新日期、复测和反馈入口。

这个顺序使普通用户在前三段理解公平性，需要审核的用户在后四段找到判定、证据与边界。FAQ 仍回答用户问题，不在方法页复制一组折叠问答；单次测试的截图、完整轨迹和逐题判分留在测试详情页。

## 不建议的设计方向

- 不要仅把现有四步流程改成更大的数字、更多线条或更精美的卡片；问题在信息不足，不在装饰不足。
- 不要照搬论文的 `Introduction → Related Work → Methodology → Experiments`；官网用户首先要知道“这对结果意味着什么”。
- 不要用多层 taxonomy 、数学公式或统计图表替代任务级证据；样本量不支持时应直说。
- 不要将记忆、搜索、Deep Research 的所有具体题目和细则塞入总方法页。
- 不要使用“完全公平”、“完全可复现”、“全面评估”等超出证据的承诺；闭源 Agent、变动网页和云端模型只能做条件化复现。
- 不要只展示“已发布”的成功证据；异常、评测故障、补测和规则修正是可信度的一部分。

## 一句话的设计判断

**方法页应让用户在不阅读一份学术论文的情况下，明白 DSHEval 的结果是如何产生的；当用户要质疑某一个结论时，页面又能把他带到对应规则和原始证据。**
